# RxCheck Claim-Evidence Matrix

This matrix is intended for design science manuscript preparation. It maps defensible claims to concrete repository evidence and gives conservative wording. Claims are limited to what the current codebase supports.

## Supported Claims

| Claim | Supporting Evidence | Safe Wording | Limitations |
|---|---|---|---|
| RxCheck is a pharmacist-facing interaction review prototype. | `README.md`; `frontend/src/components/Layout.jsx`; `frontend/src/components/PatientList.jsx`; `app/api/patients.py::ensure_default_user` creates a "Default Pharmacist". | "RxCheck is a pharmacist-facing prototype for reviewing medication interaction findings." | No authentication verifies that a user is actually a pharmacist. |
| The current database backend is Postgres. | `app/core/config.py` default `DATABASE_URL`; `app/db/session.py` engine setup; `requirements.txt` includes `psycopg2-binary` and `asyncpg`; `scripts/init_db.py` enables Postgres extensions; models use `UUID`, `JSONB`, `ARRAY`. | "The current implementation targets Postgres." | A leftover local SQLite file may exist, but it is not the active runtime backend. |
| SQLite is not currently interchangeable by changing only the connection string. | `app/models/check.py` uses Postgres `ARRAY`/`JSONB`; `app/models/interaction.py` uses `JSONB`; `scripts/import_ddinter.py` uses psycopg2 and Postgres `ON CONFLICT`. | "The code is now Postgres-oriented and would require compatibility work to support SQLite again." | SQLAlchemy provides some portability, but current model/script choices are Postgres-specific. |
| Interaction detection is deterministic and database-backed. | `app/services/orchestrator.py::run_interaction_check`; `app/models/interaction.py`; `scripts/import_ddinter.py`. | "RxCheck determines interaction existence from imported database rows, not from an LLM." | Interaction completeness depends on imported source data. |
| The LLM does not decide whether an interaction exists. | `app/api/interactions.py::explain_finding` requires an existing finding; `app/services/llm.py::generate_explanation` loads an existing `Interaction` and `InteractionCheckFinding`. | "The LLM explanation layer is downstream of deterministic interaction detection." | The LLM can still produce imperfect explanations. |
| Active placeholder drugs are excluded from interaction checks. | `app/models/drug.py::Drug.is_placeholder`; `app/services/orchestrator.py` filters `Drug.is_placeholder.is_(False)`; `app/services/checks.py::medications_for_interaction_checks`. | "Unresolved placeholder drugs remain in the medication profile but are excluded from interaction checking." | This can make interaction results incomplete when unresolved drugs are clinically relevant. |
| Drug-disease interactions are filtered by active patient conditions. | `app/services/orchestrator.py` DDSI query filters `Interaction.condition_id.in_(select(PatientCondition.condition_id)...resolved_date.is_(None))`. | "DDSI findings are surfaced only when the patient has the matching active condition recorded." | Accuracy depends on condition data being complete and correctly entered. |
| Drug-food interactions are not condition-gated. | `app/services/orchestrator.py` DFI query filters active drugs and `InteractionType.DFI` only. | "DFI findings are queried for active drugs regardless of patient condition profile." | The prototype does not model actual patient diet or food exposure. |
| DDI pairs are canonicalized to avoid duplicate ordering. | `app/models/interaction.py` check constraint `drug_a_rxcui < drug_b_rxcui`; `app/services/orchestrator.py` sorts combinations; `scripts/import_ddinter.py` sorts RxCUIs. | "DDI pairs are stored and queried in canonical lexicographic RxCUI order." | Depends on all import/write paths respecting the same ordering. |
| Check runs store medication snapshots. | `app/models/check.py::InteractionCheckRun.medications_snapshot`; `app/services/orchestrator.py` builds `medication_snapshot`. | "Each check run stores a JSON snapshot of the medication list used at run time." | Snapshot does not include every possible patient context, such as full condition history or labs. |
| Findings store run-time severity/source snapshots. | `app/models/check.py::InteractionCheckFinding`; `app/services/orchestrator.py` stores `max_severity_at_run`, `sources_at_run`, `sources_conflicted`, `suppressed_by_ack`. | "Each finding stores run-time severity, source, conflict, and suppression fields." | Source dataset version is not separately versioned. |
| Acknowledgments suppress future matching findings without deleting them. | `app/models/audit.py::InteractionAcknowledgment`; `app/services/orchestrator.py` marks `suppressed`; `frontend/src/components/InteractionResults.jsx` groups suppressed items. | "Acknowledged interactions are returned as suppressed rather than removed." | Suppression is tied to severity threshold; no advanced clinical review workflow exists. |
| Acknowledgment suppression is invalidated by severity escalation. | `app/services/orchestrator.py` compares `ack.severity_at_ack` with current `summary.max_severity`. | "An acknowledgment suppresses only if its stored severity is at least the current severity." | No automated source-update scenario is tested. |
| Overrides are persisted. | `app/models/audit.py::InteractionOverride`; `app/api/interactions.py::override_finding`. | "Override actions are stored with finding ID, user ID, action, severity, note, and timestamp." | Overrides do not currently change future check behavior. |
| Selected audit events are written for acknowledgments and overrides. | `app/models/audit.py::AuditEvent`; `app/api/interactions.py` writes `interaction_override`, `interaction_acknowledged`, `interaction_acknowledgment_removed`. | "The prototype writes selected audit events for review and override actions." | No read-access audit or immutable audit subsystem exists. |
| RxNorm is used for medication-name normalization. | `app/services/normalization.py`; `app/api/patients.py::create_patient_medication`. | "RxCheck uses NIH RxNorm APIs to resolve typed medication names to ingredient-level RxCUIs." | Runtime normalization depends on network availability unless aliases already exist. |
| Normalization writes aliases back to the database. | `app/services/normalization.py::add_alias`; `DrugAlias` model. | "Resolved names and misspellings can be stored as local aliases for future lookup." | No scheduled RxNorm refresh job exists. |
| Unresolved medication names are recorded. | `app/services/normalization.py::_record_unresolved`; `app/models/drug.py::UnresolvedDrugEntry`. | "Unresolved medication names are tracked in an unresolved queue and represented by placeholder drugs." | There is no full manual-resolution UI. |
| The real DDInter importer uses bulk Postgres upserts. | `scripts/import_ddinter.py` imports psycopg2 `execute_values`; `bulk_upsert_interactions`; `bulk_upsert_assertions`. | "The DDInter importer uses bulk Postgres inserts with conflict handling for interactions and assertions." | Current importer handles DDI-formatted files only. |
| Source assertions preserve raw source severity and raw payload. | `app/models/interaction.py::InteractionSourceAssertion`; `scripts/import_ddinter.py::bulk_upsert_assertions`. | "Source assertions preserve source severity text and a JSON raw payload." | Current real DDInter files may not include rich mechanism/management fields. |
| Hub scores are implemented. | `app/services/checks.py::get_hub_scores`; `app/services/orchestrator.py` passes hub scores to `build_summary`. | "RxCheck computes per-drug interaction counts for the active medication list and includes them in summaries." | Hub score is a count heuristic, not a validated risk score. |
| OpenFDA is used as explanation context, not an interaction source. | `app/services/openfda.py`; `app/services/llm.py` includes label excerpts in RAG context; orchestrator does not call OpenFDA. | "OpenFDA label text is used as optional explanatory context." | Label text is not persisted as a versioned local corpus. |
| The frontend supports the core demo workflow. | `frontend/src/components/PatientList.jsx`; `PatientDetail.jsx`; `MedicationList.jsx`; `InteractionResults.jsx`; `InteractionCard.jsx`. | "The frontend supports a demo workflow from patient creation/seed through medication review and interaction explanation." | UI is prototype-level and lacks auth/audit-history screens. |
| The app is deployed as a single Railway service. | `railway.toml`; `Procfile`; `app/main.py` static frontend serving. | "The repository is configured for a single Railway service that builds the frontend and serves it from FastAPI." | Operational hardening is incomplete. |

## Claims To Avoid Or Flag As Unsupported

| Unsupported Claim | Why It Should Not Be Made | Safer Alternative |
|---|---|---|
| "RxCheck is clinically validated." | No gold-standard evaluation or clinical study exists in the repository. | "RxCheck is a prototype with planned formative evaluation." |
| "RxCheck is FDA-cleared." | No regulatory clearance evidence exists. | "RxCheck is not FDA-cleared and is not intended for clinical use." |
| "RxCheck is HIPAA-compliant." | No auth, encryption, access logging, BAA, or compliance controls are implemented. | "The schema includes some audit-oriented structures but the app is not HIPAA-ready." |
| "RxCheck provides complete DDI coverage." | Coverage depends on imported DDInter rows and normalization success. | "RxCheck checks interactions present in its imported database." |
| "The LLM improves detection accuracy." | The LLM is not used for detection. | "The LLM provides optional explanations for already-detected findings." |
| "The system is cost-effective." | No formal cost-effectiveness analysis exists. | "The architecture is designed to be cost-conscious by using open-source components and optional paid services." |
| "SQLite is the current production database." | Current config/models/scripts target Postgres. | "RxCheck currently targets Postgres." |
| "All audit needs are met." | Read access, immutable audit, auth-bound identity, and compliance logging are missing. | "Selected review and override actions are persisted for prototype auditability." |
| "OpenFDA validates interaction existence." | OpenFDA is only used for label context in explanations. | "OpenFDA provides optional label excerpts for explanation context." |
| "Overrides affect future checks." | Overrides are persisted but not used by the orchestrator. | "Overrides are recorded for review; future check behavior is not changed by overrides." |
