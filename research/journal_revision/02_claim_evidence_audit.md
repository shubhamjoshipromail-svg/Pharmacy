# RxCheck Claim–Evidence Audit

## Audit method

Claims were extracted from `paper/rxcheck_manuscript_0.1v.md` and checked against repository commit `6b763c03a69e33031f196eceb598899ee08a1cba`. “Fully supported” means that the inspected code or recorded artifact directly supports the narrowly worded claim. It does not imply clinical validity. “Partially supported” means that the design or one tested path exists but the broader wording exceeds the evidence. “Requires verification” means that a historical result is recorded but cannot be independently reconstructed from the repository as committed.

## Evidence table

| Claim in the paper | Evidence in the repository or project materials | Level of support | Problem or caveat | Recommended revision |
|---|---|---|---|---|
| RxCheck is a pharmacist-facing drug-interaction review system. | `frontend/src/components/*`; `README.md`; `app/api/patients.py::ensure_default_user` creates a “Default Pharmacist.” | partially supported | The interface is pharmacist-oriented, but there is no authentication, credential check, or pharmacist user study. | “RxCheck is a pharmacist-oriented research prototype for reviewing drug-interaction findings.” |
| RxCheck is implemented with FastAPI, React, and Postgres. | `app/main.py`; `frontend/package.json`; `app/db/session.py`; Postgres-specific models and importer. | fully supported | Versions are not pinned; Postgres configuration contains an exposed credential. | Retain the stack description, add commit SHA, and report versioned environment after remediation. |
| Interaction existence is determined by deterministic stored-data lookup rather than an LLM. | `app/services/orchestrator.py::run_interaction_check`; no LLM/OpenFDA/RxNorm call on that path; scenarios 1, 5, and 24–26 in `research/evaluation_results.json`. | fully supported | Only the inspected paths are covered; absence of a database row produces no finding. | “On the evaluated core path, findings are created only from stored interaction rows.” |
| The LLM cannot create a new interaction finding. | `POST /findings/{finding_id}/explain` first loads a persisted finding; `generate_explanation` runs downstream. | fully supported | This is an endpoint/architecture boundary, not proof that generated prose is accurate or harmless. | Retain with an immediate qualification about explanation risk. |
| RxCheck uses “strict RAG.” | `app/services/llm.py` constructs context from one stored assertion, severity/source data, and optional OpenFDA excerpts. | partially supported | No retrieval benchmark, passage/citation entailment, formal source binding, or completed explanation evaluation; only the first assertion supplies mechanism/management. | Replace “strict RAG” with “structured, evidence-bounded explanation context.” |
| LLM output is schema-validated. | `_parse_explanation_payload` checks JSON parsing, seven required keys, and that `sources_used` is a list; `_validate_drug_mentions` scans names. | partially supported | No Pydantic/JSON Schema validation of field types, confidence values, severity preservation, sources, or factuality. | Medication input is normalized to ingredient-level RxNorm concepts. | `app/services/normalization.py` exact, approximate, NDC, and `related.json?tty=IN` paths. | partially supported | First-hit and fuzzy-score heuristics are unvalidated; combination products, ambiguity, outages, and real-world accuracy are not evaluated. | “The workflow attempts to map input toward an RxNorm ingredient concept using implementation-defined heuristics.” |
| Unresolved medication input is explicitly represented and excluded from checking. | `_record_unresolved`; `Drug.is_placeholder`; orchestrator filter; scenarios 4 and 5. | fully supported | Exclusion can create clinically important false negatives; result-level warning salience was not evaluated. | Retain, and state that completeness is reduced until a human resolves the input. |
| DDI pairs are canonicalized. | Interaction check constraint; sorted importer pairs; set of sorted medication combinations; scenario 2. | fully supported | Duplicate active rows can still create a same-RxCUI pair in `total_pairs_checked`, although findings are deduplicated. | “Canonical ordering prevents A–B/B–A duplicate stored findings; medication-list deduplication remains incomplete.” |

| RxCheck represents source disagreement. | `build_summary` flags more than one stored severity; scenario 9; profile reports 174 interactions with distinct asserted severities. | partially supported | The profile does not establish source independence, quality, recency, or clinical disagreement; fixture rows are included. | “The prototype flags stored severity-label differences without adjudicating them.” |

| Acknowledgment and escalation logic manages alert burden. | Acknowledgment model; orchestrator suppression; scenarios 21 and 22. | partially supported | Architecture behavior is tested, but no alert-fatigue or workflow outcome is measured. | “The prototype implements acknowledgment suppression and severity-escalation resurfacing intended to manage repeated presentation.” |
| Overrides are persisted. | `InteractionOverride`; `override_finding`; scenario 19. | fully supported | Overrides do not alter or annotate later findings; identity is unauthenticated. | “Finding-level override actions are stored for prototype review but do not change subsequent checks.” |
| Review activity is auditable. | Check runs/findings, acknowledgments, overrides, selected `AuditEvent` writes, and explanation metadata. | partially supported | Checks with fewer than two verified medications are not persisted; no read audit, immutability, authenticated identity, or compliance controls. | Use “audit-oriented persistence of selected runs, findings, and review actions.” |
| OpenFDA provides explanation context, not interaction detection. | OpenFDA is imported only by `app/services/llm.py`; orchestrator has no OpenFDA dependency; scenario 25. | fully supported | Generic-name fallback may select the wrong label; content and exact version are not persisted; non-404 failures can propagate. | Retain and describe label evidence as optional, heuristic, and unvalidated. |
| Core checking does not require Anthropic, OpenFDA, or RxNorm at check time. | Service boundaries and scenarios 24–26. | fully supported | RxNorm may still be required to add unseen medication names; the evaluation mocks boundary calls on selected paths only. | “Previously normalized medication lists can be checked without those services on the evaluated core path.” |
| The architecture is frugal or suitable for budget-constrained pharmacies. | `research/cost_constrained_design.md`; optional-service separation; open-source stack. | partially supported | No measured costs, comparator, setting study, total-cost analysis, bandwidth test, operations model, or pharmacy evaluation. | Recast as “cost-conscious service separation”; remove frugality from title and conclusions until measured. |
| The evaluation passed 26 of 26 scenarios and used no external APIs. | Timestamped `research/evaluation_results.json` and `.md`; evaluator source. | fully supported as a recorded result | The result is historical, self-authored, database-writing, and not independently rerunnable from archived data/environment. A perfect aggregate does not indicate clinical performance. | “A recorded June 9, 2026 formative run passed all 26 predefined synthetic architecture assertions; no external APIs were invoked on those paths.” |
| The evaluation is reproducible. | Evaluator and results are committed; explicit write flag; scenario evidence is recorded. | requires verification | Missing source data/version/checksums, database snapshot, populated migration, dependency lock, teardown, and safe default configuration. | Replace with “the repository provides an evaluation script and recorded outputs; a clean independent reproduction remains required.” |
| The profiled database contained 152,416 interactions and 172,714 assertions. | `research/data_profile.json` generated June 9, 2026. | requires verification | Live database is not archived; exact DDInter release is unknown; totals include five identified fixture interactions and six fixture assertions. | Report as timestamped configured-database observations and include fixture-adjusted counts only after author verification. |
| The stored data form a non-trivial structured artifact. | Schema, importer, recorded counts, and research inventory. | partially supported | “Non-trivial” is subjective; quantity does not establish quality, coverage, or validity. | Describe the tables and timestamped counts directly; omit evaluative adjectives. |
| Database absence is a meaningful negative result. | Scenario 15 confirms no finding for an unstored pair. | fully supported as software behavior | A missing row can mean source/import/normalization failure and must not be interpreted as clinical non-interaction. | Add a prominent “no stored finding is not evidence of no clinical interaction” warning. |
| The explanation-quality rubric contributes evaluation evidence. | `research/explanation_quality_rubric.md` and template exist. | unsupported as a result | The rubric is an unvalidated proposed instrument and no completed scored sample is reported. | Present it as future evaluation material or complete and report it as formative boundary-adherence assessment. |

DDInter data have separate CC BY-NC-SA terms. | Add an explicit software license and third-party data/license notice after author/legal review. |

## Audit conclusion

The central architecture claim is supported: the inspected core checker creates findings from stored rows, and the LLM endpoint is downstream of a finding. Most risk arises when the paper generalizes this boundary into stronger claims about grounding, reproducibility, clinical usefulness, multi-source evidence, or affordability. The revision should make the evaluated unit explicit: **software architecture behavior under synthetic fixtures**, not clinical decision-support performance.
