# Protocol: Isolated Architecture Reproduction

## Research question

Can the committed 26-scenario RxCheck architecture evaluation be reproduced from an empty, disposable local PostgreSQL database without using the repository's configured remote database or calling RxNorm, OpenFDA, or Anthropic?

## Rationale

The research-readiness review, claim–evidence audit, journal-readiness review, and remaining-author-actions checklist all identify clean evaluation reproduction as a submission-critical gap. The historical June 9, 2026 result is useful evidence, but its database was not archived, its fixtures persist, its environment is incompletely specified, and the repository's default database configuration is unsafe to use.

## Objective

Run the existing `research/evaluate_rxcheck.py::run_evaluation` function unchanged against fresh local databases and retain enough metadata and raw output for another researcher to audit the result.

## Hypothesis

All 26 predefined synthetic architecture scenarios will pass in each of three fresh-database repetitions, and the evaluator will report no paid or free external API calls.

## Inputs

- Application and evaluator code from the current research branch.
- Synthetic fixtures generated by the existing evaluator.
- PostgreSQL 16.14 built from the official source release.
- A temporary Python 3.12 virtual environment resolved from the repository's unpinned `requirements.txt`.

No DDInter source files, clinical cases, real patient records, live project database, or model-provider credentials are used.

## Procedure

1. Build PostgreSQL 16.14 outside the repository and verify the downloaded source archive against its publisher-provided SHA-256 file.
2. Create a temporary Python environment from `requirements.txt` outside the repository.
3. Initialize one disposable PostgreSQL cluster bound only to `127.0.0.1` on an ephemeral port.
4. For each of three repetitions, create a new empty database with a unique name.
5. Have the Python harness verify that the database hostname and server address are loopback-only and that the database has no pre-existing tables.
6. Import all SQLAlchemy models and call `Base.metadata.create_all()`.
7. Call the unchanged `run_evaluation()` function and save its complete scenario-level payload plus environment, source-hash, schema, timing, and row-count metadata.
8. Require 26 of 26 scenarios to pass, both external-API flags to remain false, and the expected 19 tables to be created.
9. Summarize agreement across repetitions.
10. Stop the PostgreSQL server and delete the temporary cluster automatically.
11. Verify that the original manuscript and historical evaluation artifacts are unchanged.

## Metrics

- Scenarios passed, failed, and total per repetition.
- Scenario-name and pass/fail agreement across repetitions.
- External paid/free API flags.
- Pre- and post-schema table counts.
- Synthetic row counts after each run.
- Wall-clock evaluation duration.
- Source-file SHA-256 hashes and evaluated-source Git commit.
- Python, package, operating-system, architecture, and PostgreSQL versions.

## Success criteria

The task passes only if all of the following are true:

1. Three fresh-database repetitions complete.
2. Every repetition reports 26 passed, 0 failed.
3. Every repetition reports no paid or free external API calls.
4. Each database has zero tables before setup and 20 expected tables after setup.
5. Scenario names and pass/fail outcomes agree across repetitions.
6. The connection guard and server-side address check confirm loopback-only use.
7. The temporary cluster is stopped and removed.
8. The original manuscript and historical evaluation files remain unchanged.

Any unmet criterion is a failed or inconclusive reproduction and must be reported as such.

## Reproducibility command

From the repository root, after PostgreSQL and the Python environment are prepared outside the repository:

```bash
PG_BIN=/path/to/postgresql/bin \
PYTHON_BIN=/path/to/python \
bash research/journal_revision/evidence/01_isolated_architecture_reproduction/scripts/run_repetitions.sh
```

The exact local paths used for this run are recorded in the execution log, but they are not required locations.

## Prespecified limitations

- The scenarios and expected outcomes were authored within the same project.
- The evaluation verifies software architecture behavior, not clinical correctness, completeness, or safety.
- Synthetic fixtures do not exercise the real DDInter import or medication normalization against the live RxNorm service.
- `Base.metadata.create_all()` is used because the committed Alembic migration cannot construct the schema; this test therefore does not validate migration reproducibility.
- Dependency resolution starts from unpinned requirements, so the captured resolved environment is reproducible as evidence but the repository itself remains unpinned.
- Three repetitions detect gross nondeterminism but are not a statistical reliability study.
